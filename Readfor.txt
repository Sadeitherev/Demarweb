READFOR: памятка владельца проекта Demar Alyans

Цель файла
---------
Этот файл нужен как рабочая инструкция для будущего использования сайта. Если проект будет меняться, этот файл можно обновлять, чтобы всегда было понятно:
- как запустить сайт локально;
- как проверить, что он работает;
- что нужно сделать перед показом работодателю или клиенту;
- что нужно сделать для реального запуска на сервере;
- какие действия должен выполнить владелец проекта вручную.


1. Что находится в проекте
--------------------------
Проект сделан как монорепозиторий.

Основные папки:
- apps/web - сайт на Next.js.
- apps/api - backend API на NestJS.
- packages/db - Prisma, схема базы данных и db helpers.
- packages/validation - общие схемы валидации форм.
- infra - инфраструктурные файлы, сейчас там Docker Compose для PostgreSQL.

Важные файлы:
- .env.example - пример переменных окружения.
- .env - локальные секреты. Этот файл нельзя загружать на GitHub.
- README.md - короткая инструкция для разработчика/работодателя.
- Readfor.txt - подробная памятка для владельца проекта.
- TODO.md - общий список будущих задач.
- turbo.json - настройки TurboRepo.
- .gitignore - список файлов, которые Git не должен загружать.
- .vscode/settings.json - настройки VS Code, чтобы редактор не индексировал .next, node_modules и другие тяжелые папки.


2. Как запустить проект локально
--------------------------------
Открыть PowerShell в корне проекта:

D:\Project\Demaralyance

Установить зависимости:

npm install

Создать локальный .env:

Copy-Item .env.example .env

После этого открыть .env и заменить все значения вида replace-with... на реальные длинные секреты.

Запустить PostgreSQL:

docker compose --env-file .env -f infra/docker-compose.yml up -d

Сгенерировать Prisma client:

npm run db:generate

Применить миграции:

npm run db:migrate

Запустить API:

npm run dev:api

Запустить сайт на 3000 порту:

npm run dev:web

Открыть сайт:

http://localhost:3000


3. Как проверить, что проект не сломан
--------------------------------------
Перед показом, коммитом или деплоем всегда запускать:

npm run build --workspace web

npm run build --workspace api

Обе команды должны проходить без ошибок.

Также нужно вручную проверить:
- открывается ли http://localhost:3000;
- работает ли навигация по секциям;
- корректно ли отображается мобильная версия;
- отправляется ли форма заявки;
- отправляется ли форма калькулятора;
- сохраняется ли заявка в базе данных;
- не появляются ли ошибки в терминале API и web.


4. Как работает форма заявки
----------------------------
Фронтенд отправляет заявки на:

/api/v1/leads

В Next.js настроен rewrite:

/api/* -> API_ORIGIN/api/*

Локально API_ORIGIN по умолчанию:

http://localhost:4000

В production API_ORIGIN нужно заменить на адрес backend API.

Пример:

API_ORIGIN=https://api.demaralyans.by

Или, если web и api будут на одном домене через reverse proxy:

API_ORIGIN=http://localhost:4000

а Nginx будет проксировать внешние запросы.

Примерная схема:

Шаг 12. Подключить HTTPS через Let's Encrypt.

Шаг 13. Проверить:

8.1. SSL/TLS сертификаты и HTTPS
--------------------------------
Для production сайт обязательно должен работать через HTTPS.

Самый простой вариант - бесплатные сертификаты Let's Encrypt через Certbot.

Что нужно сделать владельцу вручную:
- купить или получить домен;
- направить DNS A-записи домена на IP сервера;
- убедиться, что домен открывается с сервера;
- открыть на сервере порты 80 и 443;
- установить Nginx и Certbot;
- получить сертификат;
- включить автоматическое обновление сертификатов.

Пример DNS:
- demaralyans.by -> IP сервера;
- www.demaralyans.by -> IP сервера;
- api.demaralyans.by -> IP сервера, если API будет на отдельном поддомене.

Порты, которые должны быть открыты:
- 80/tcp для HTTP и проверки Let's Encrypt;
- 443/tcp для HTTPS;
- 22/tcp для SSH, желательно ограничить по IP, если возможно.

Пример установки на Ubuntu:

sudo apt update
sudo apt install nginx certbot python3-certbot-nginx -y

Получение сертификата для основного домена:

sudo certbot --nginx -d demaralyans.by -d www.demaralyans.by

Если API будет на отдельном поддомене:

sudo certbot --nginx -d api.demaralyans.by

После выдачи сертификата Certbot обычно сам добавляет HTTPS-настройки в Nginx.

Проверить автоматическое обновление:

sudo certbot renew --dry-run

Если команда прошла успешно, сертификаты будут обновляться автоматически.

Что важно проверить после подключения HTTPS:
- http://demaralyans.by перенаправляет на https://demaralyans.by;
- https://demaralyans.by открывается без предупреждений браузера;
- https://www.demaralyans.by либо открывается, либо перенаправляет на основной домен;
- формы сайта отправляются без mixed content ошибок;
- API доступен по HTTPS или через безопасный reverse proxy;
- в production cookies имеют флаг Secure;
- HSTS включен только после того, как HTTPS точно работает стабильно.

Пример важных Nginx security headers:

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

Важное предупреждение про HSTS:
Не включать preload сразу. Сначала убедиться, что HTTPS стабильно работает на всех нужных доменах и поддоменах.

Где хранятся сертификаты Let's Encrypt:

/etc/letsencrypt/live/your-domain/fullchain.pem
/etc/letsencrypt/live/your-domain/privkey.pem

Нельзя:
- копировать private key в GitHub;
- пересылать private key в чатах;
- хранить сертификаты в проекте;
- отключать автообновление сертификатов;
- открывать PostgreSQL наружу ради HTTPS. HTTPS относится к web/API, не к базе.

Если сайт размещается не на VPS, а на Vercel/Netlify/Cloudflare Pages:
- сертификаты обычно подключаются автоматически;
- нужно только правильно настроить DNS;
- HTTPS включается в панели хостинга;
- Nginx и Certbot могут быть не нужны.

10. Безопасность
----------------
Текущая база безопасности уже есть:
- NestJS ValidationPipe;
- DTO validation;
- rate limiting для лидов;
- helmet;
- CORS config;
- cookies config;
- .env.example вместо настоящих секретов.

Но для production еще нужно:
- включить HTTPS;
- настроить HSTS;
- настроить CSP;
- настроить secure cookies;
- включить CSRF-защиту для mutating requests, если используются cookie sessions;
- ограничить CORS только реальными доменами;
- не показывать stack trace пользователям;
- проверять зависимости через npm audit;
- обновлять зависимости;
- настроить backup базы;
- настроить firewall;
- закрыть прямой доступ к PostgreSQL извне.

Команды проверки зависимостей:

npm audit

npm audit fix

Сначала читать, что именно будет исправлено. Не применять слепо breaking changes.


11. Backup базы данных
----------------------
Перед production нужно настроить регулярный backup PostgreSQL.

Минимальный подход:
- ежедневный pg_dump;
- хранить копии минимум 7-14 дней;
- хранить копии не только на том же сервере;
- периодически проверять восстановление из backup.

Без backup сайт может потерять все заявки и данные портфолио.

9.1. Админ-панель: зачем нужна и как с ней работать
---------------------------------------------------
Админ-панель пока не реализована полностью, но она запланирована как важный следующий этап проекта.

Зачем нужна админ-панель:
- смотреть заявки, которые отправляют пользователи через формы;
- менять статус заявок: новая, в работе, обработана, архив;
- добавлять и редактировать проекты/портфолио;
- загружать фотографии объектов;
- менять тексты услуг, описания, контакты и SEO-данные без правки кода;
- управлять отзывами, если они будут настоящими;
- видеть историю изменений, кто и что поменял.

Что можно будет делать через админку в будущем:
- входить по логину и паролю;
- просматривать список заявок;
- открывать детальную карточку заявки;
- добавлять комментарии менеджера;
- создавать проекты;
- редактировать проекты;
- публиковать или скрывать проекты;
- менять порядок изображений в галерее;
- добавлять alt-тексты для изображений;
- архивировать старые записи.

Что обязательно должно быть в безопасной админке:
- отдельная страница /admin;
- логин только по HTTPS;
- пароли хранить только в виде hash, лучше Argon2 или bcrypt;
- HttpOnly Secure session cookie;
- CSRF-защита для всех действий, которые меняют данные;
- rate limiting на login;
- блокировка или задержка после множества неудачных попыток входа;
- роли пользователей, если админов будет несколько;
- audit log: кто, когда и что изменил;
- запрет индексации /admin через robots.txt и reverse proxy;
- запрет доступа к /admin без авторизации;
- валидация всех данных на backend;
- ограничение размера загружаемых файлов;
- проверка типа изображений;
- хранение файлов в безопасной папке или внешнем storage.

За чем следить владельцу:
- не использовать простой пароль администратора;
- не давать один общий пароль всем сотрудникам;
- отключать доступ бывшим сотрудникам;
- периодически менять пароли;
- проверять audit log;
- делать backup базы перед массовыми правками;
- не загружать подозрительные файлы;
- не вставлять в тексты HTML/скрипты из неизвестных источников;
- проверять, что /admin не открывается без логина;
- проверять, что cookies в production имеют Secure и HttpOnly;
- проверять, что админка работает только через HTTPS.

Минимальный безопасный сценарий работы администратора:
1. Открыть https://domain.by/admin.
2. Войти под личным логином и паролем.
3. Проверить новые заявки.
4. Связаться с клиентом.
5. Изменить статус заявки.
6. При необходимости добавить комментарий.
7. Выйти из админки после работы.

Что нельзя делать в админке:
- хранить пароли клиентов или сотрудников в открытом виде;
- публиковать персональные данные клиентов на сайте;
- загружать чужие изображения без разрешения;
- давать доступ подрядчикам без ограничения прав;
- оставлять админку открытой на чужом компьютере;
- отключать audit log;
- отключать rate limiting на login.

Как понять, что админка готова к production:
- вход работает только по HTTPS;
- пароль хранится в hash;
- неправильный пароль не раскрывает, существует ли пользователь;
- после 5-10 ошибок вход временно ограничивается;
- все POST/PUT/PATCH/DELETE защищены CSRF или другим механизмом;
- обычный пользователь не может открыть /admin;
- админ не может выполнить действие без прав;
- все действия пишутся в audit log;
- build web и api проходит;
- backup базы настроен;
- есть инструкция восстановления доступа администратора.

Если пароль администратора потерян:
- не создавать временный открытый endpoint для сброса пароля;
- сделать безопасный server-side script для смены пароля;
- выполнить его только на сервере;
- записать действие в audit log;
- после восстановления доступа сменить временный пароль.

Важно:
Админ-панель нельзя делать "на скорую руку" без безопасности. Это самая чувствительная часть проекта, потому что через нее можно получить доступ к заявкам, персональным данным и публичному содержимому сайта.


15. Если что-то сломалось
-------------------------
Порядок действий:

1. Проверить, где ошибка:
- web;
- api;
- database;
- env;
- network/proxy;
- GitHub/deploy.

2. Запустить build:

npm run build --workspace web
npm run build --workspace api

3. Проверить .env:
- DATABASE_URL;
- DIRECT_URL;

16. Важное правило
------------------
Перед любым важным действием:
- не удалять .env;
- не делать git reset --hard без полного понимания;
- не пушить секреты;
- не обновлять зависимости вслепую;
- сначала делать backup, если уже есть реальные данные.
